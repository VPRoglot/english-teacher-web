> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Приложение готово к работе на одном российском VPS:
- prod-compose с nginx + certbot (TLS, заголовки безопасности, CSP);
- CD из GitHub Actions в GHCR и на сервер по SSH, со smoke-проверкой и откатом;
- зашифрованные ежедневные бэкапы в S3 с ротацией и проверкой восстановления в CI;
- Sentry в api, worker и web, heartbeat-пинги ежедневных задач;
- обезличивание заявок и `purge-family` (152-ФЗ);
- полный e2e-набор Playwright на prod-подобном стеке;
- все хвосты планов 2–6.

**Architecture:**
- **Backend.**
  - Новых модулей нет.
  - `core/observability.py` — Sentry и heartbeat.
  - `leads/retention.py` — обезличивание заявок.
  - `families/purge.py` — оркестратор полного удаления семьи. Каждый модуль удаляет свои строки сам, через свою функцию сервиса (правило R8 плана 5).
  - Проброс реального IP — `ProxyHeadersMiddleware` из uvicorn, включается настройкой.
- **Инфраструктура: четыре своих образа в GHCR:**
  - `english-tutor-backend`;
  - `english-tutor-frontend`;
  - `english-tutor-nginx` — конфиг вшит в образ, self-signed запасной сертификат, перечитывание сертификата;
  - `english-tutor-backup` — `pg_dump` → `age` → S3 с ротацией.
  
  `infra/docker-compose.prod.yml` поверх базового файла. На сервере лежит клон репозитория. `infra/scripts/deploy.sh <sha>` переключает `IMAGE_TAG`, делает `pull` → `migrate` → `up -d`, затем smoke-проверку, а при неудаче откатывается.
- **E2E.**
  - Отдельный пакет `e2e/` с Playwright, запускается в контейнере `mcr.microsoft.com/playwright`. Устанавливать браузеры на хост не нужно.
  - Стек: `docker-compose.yml` + `docker-compose.prod.yml` + `docker-compose.e2e.yml` (MinIO, домен `tutor.test`, self-signed TLS через тот же nginx).

**Уточнения спеки, принятые в этом плане:**
1. **Обезличивание.** Политика конфиденциальности уже обещает: «Заявки, по которым ребёнок не стал учеником, обезличиваются через 12 месяцев». Это шире спеки 6.4 («rejected старше 12 месяцев»), и обещание пользователю приоритетнее. Поэтому обезличивается любая заявка в статусе ≠ `converted`, у которой с последней смены статуса (`max(lead_status_history.changed_at)`, а без истории — `created_at`) прошло не меньше 12 календарных месяцев (`relativedelta(months=12)`). Rejected-заявки входят в это правило как частный случай.
   - **Заменяются:**
     - `parent_name` и `child_name` → `"Обезличено"`;
     - `phone` → `""`;
     - `messenger_handle`, `goal`, `preferred_time`, `tutor_comment`, `reject_reason` → `NULL`;
     - `lead_status_history.comment` → `NULL`;
     - выставляется `anonymized_at = now`.
   - **Остаются для статистики:** `child_age`, `contact_method`, `status`, UTM-метки, `consent_at`, `created_at`.
2. **`purge-family`:**
   - удаляет только архивную семью (`archived_at IS NOT NULL`), иначе отказ — защита от случайного удаления;
   - удаляет вместе с семьёй:
     - запросы на перенос (раньше занятий — FK RESTRICT);
     - занятия, серии и заметки детей;
     - заявки с `family_id` этой семьи — вместе с их историей и пробными занятиями. В них ПДн той же семьи;
     - приглашения;
     - учётные записи родителей и детей вместе со ссылками сброса пароля;
   - после коммита удаляет Redis-сессии этих пользователей;
   - всё выполняется в одной транзакции;
   - CLI спрашивает подтверждение, а `--yes` его пропускает.
   
   Политика конфиденциальности дополняется строкой о бэкапах: удалённые данные исчезают из резервных копий не позднее чем через 6 месяцев.
3. **Миграции при откате только расширяющие.** `deploy.sh` при неудачной smoke-проверке возвращает прошлый образ, но не откатывает схему БД. Поэтому миграция обязана быть совместимой с кодом предыдущего релиза: столбцы и таблицы удаляются отдельным релизом, после того как код перестал их использовать. Правило записывается в `infra/README.md`.
4. **CSP без nonce.** Nonce сделал бы весь лендинг динамическим (`cacheComponents`), поэтому `script-src 'self' 'unsafe-inline'` плюс домен SmartCaptcha. Риск XSS низкий: React экранирует вывод, Markdown отрисовывается без HTML. JSON-LD (`application/ld+json`) не исполняется и CSP не затрагивает.
5. **Браузерный Sentry отправляет события через туннель** `/monitoring` (`tunnelRoute` у `@sentry/nextjs`). Отдельного домена в CSP `connect-src` не нужно, блокировщики не мешают.
6. **Бэкапы шифруются** `age` на публичный ключ (`BACKUP_AGE_RECIPIENT`). Приватный ключ хранится у владельца вне сервера и подаётся только при восстановлении. Бакет бэкапов обязан отличаться от публичного медиа-бакета, иначе скрипт завершается с ошибкой.
7. **Smoke-проверка deploy** — `curl -k --resolve $DOMAIN:443:127.0.0.1`: проверяется приложение, а не сертификат. Сертификат и доступность снаружи проверяет внешний uptime-монитор (README).
8. **Heartbeat.**
   - Задачи `lessons.materialize_series` и `leads.anonymize_stale` и контейнер backup после успеха делают GET на необязательные URL `HEARTBEAT_*` (Healthchecks.io или heartbeat-монитор GlitchTip). Так в prod проверяется, что cron действительно срабатывает: пропуск пинга даёт оповещение.
   - Ошибка пинга логируется и задачу не ломает.

## Review Focus

1. **Неудачный релиз:**
   - новый образ не проходит smoke-проверку → `deploy.sh` возвращает прошлый `IMAGE_TAG` и прошлый коммит, поднимает их и выходит с кодом 1;
   - сайт продолжает работать на старой версии.
   
   Тест в Task 7 (`test-deploy.sh` с заглушками `docker`/`git`/`curl`).
2. **Пересоздание контейнера api при деплое.** У нового контейнера другой IP, и nginx не должен продолжать слать запросы на старый: используется `resolver 127.0.0.11` + `proxy_pass` с переменной. Тест в Task 5: заглушка upstream пересоздаётся, `curl` через nginx снова получает 200.
3. **Одноразовые токены не попадают в логи и Sentry:**
   - `/invite/<token>`, `/reset/<token>`, `/api/auth/invitations/<token>`, `/api/auth/password-resets/<token>` маскируются (`***`) в access-логе nginx, в событиях и breadcrumb'ах Sentry backend и web;
   - токен бота Telegram (`/bot<token>/`) маскируется в breadcrumb'ах Sentry.
   
   Тесты в Task 2, Task 5, Task 9.
4. **Подделка `X-Forwarded-For`:**
   - клиент присылает `X-Forwarded-For: 1.2.3.4` → upstream видит только реальный адрес клиента (nginx перезаписывает заголовок);
   - backend с доверенным прокси различает IP для rate limit: 4-я заявка с одного адреса → 429, с другого → 201.
   
   Тесты в Task 5 и Task 1.
5. **Бэкап:**
   - восстановленная из зашифрованного дампа база совпадает с исходной (число строк и выборка);
   - ротация оставляет 14 новейших дневных и 6 новейших месячных копий и никогда не удаляет только что созданную;
   - `BACKUP_S3_BUCKET == S3_BUCKET` → ошибка до дампа.
   
   Тест в Task 6.
