# Хранилище на VPS вместо внешнего S3 — дополнение к дизайну MVP

- **Дата:** 2026-10-13
- **Статус:** согласовано
- **Основной документ:** `docs/superpowers/specs/2026-10-11-english-tutor-mvp-design.md`
- **Меняет разделы:** 2.2 (контейнеры), 2.3 (файлы), 6.5 (бэкапы), 8.1 (`docker-compose.prod.yml`, контейнер `backup`)

## 1. Зачем

Владелец хочет, чтобы в MVP всё работало на одном VPS, без внешнего S3-провайдера. Бэкапы в MVP не нужны, но всё нужное для них остаётся в проекте, чтобы включить их позже без доработки кода.

## 2. Решения

| Вопрос | Решение |
|---|---|
| Где хранятся фото лендинга | MinIO внутри prod-compose на том же VPS (S3 API — код приложения не меняется) |
| Учётка приложения в MinIO | Отдельный пользователь с правами только на бакет медиа; root-учётка есть только у сервиса `minio` |
| Бэкапы в MVP | Выключены. Сервис `backup` в профиле `backup`, обычный `up` и `deploy.sh` его не запускают |
| Задел под бэкапы | Образ, скрипты, шифрование `age`, ротация и проверка восстановления в CI остаются без изменений |
| Политика конфиденциальности | Строка про бэкапы становится условной: «Если ведутся резервные копии, удалённые данные исчезают из них не позднее чем через 6 месяцев» |

## 3. Устройство

### 3.1. Сервисы prod-compose

- **`minio`:**
  - образ `cgr.dev/chainguard/minio` закреплён по digest (тот же, что в dev);
  - команда `server /data`, консоль не нужна;
  - том `miniodata`, портов наружу нет;
  - `restart: unless-stopped`, логи json-file 10m×5, лимит памяти 512 МБ.
- **`minio-init`:**
  - одноразовый, образ `cgr.dev/chainguard/minio-client:latest-dev` по digest;
  - выполняется при каждом `up` и не ломается от повторного запуска:
    1. ждёт готовности `minio`;
    2. `mc mb --ignore-existing` для бакета `${S3_BUCKET}`;
    3. `mc anonymous set download` на этот бакет;
    4. заводит пользователя `${S3_ACCESS_KEY}` / `${S3_SECRET_KEY}` (если уже есть — обновляет пароль);
    5. создаёт политику «чтение и запись только в `${S3_BUCKET}`» и привязывает её к этому пользователю.
  - Root-учётку (`MINIO_ROOT_USER` / `MINIO_ROOT_PASSWORD`) получают только `minio` и `minio-init`.
- **api:** в `depends_on` добавляется `minio-init: service_completed_successfully`. Worker и scheduler в S3 не ходят — им эта зависимость не нужна. Миграции по-прежнему вне графа `up` (профиль `migrate`), откат `deploy.sh` не трогает схему.
- **Настройки api:** `S3_ENDPOINT_URL=http://minio:9000`, `S3_ADDRESSING_STYLE=path`, `S3_REGION` — любое значение.
- **nginx:** `MEDIA_UPSTREAM=http://minio:9000/${S3_BUCKET}`, `MEDIA_UPSTREAM_HOST=minio:9000`. Проксирование `/media/` уже поддерживает http-upstream: проверка TLS действует только для https.
- **`backup`:** уходит в `profiles: ["backup"]`.

### 3.2. Переменные (`infra/prod.env.example`)

- **Новые обязательные:** `MINIO_ROOT_USER`, `MINIO_ROOT_PASSWORD` (заглушки `change-me`, как у прочих секретов).
- **Не меняются:** `S3_BUCKET`, `S3_ACCESS_KEY`, `S3_SECRET_KEY`. Теперь это бакет и учётка приложения во внутреннем MinIO. `S3_ENDPOINT_URL` и `MEDIA_UPSTREAM*` задаёт prod-compose, а не `.env`.
- **Закомментированы, со ссылкой на раздел README «Бэкапы»:** `BACKUP_*` и `HEARTBEAT_BACKUP_URL`.
- Prod-проверки backend (`change-me` в `S3_SECRET_KEY` и т. п.) остаются в силе.

### 3.3. E2E

- e2e-оверлей больше не объявляет свои `minio` и `minio-init`, а использует сервисы из prod-оверлея. Так e2e проверяет именно prod-конфигурацию хранилища.
- **Новый сценарий:** репетитор загружает фото в блок hero → на `/` появляется картинка с `src`, начинающимся на `/media/`, и запрос этой картинки через nginx отдаёт 200 с `image/*`. Сценарий проверяет всю цепочку:
  - учётку приложения;
  - анонимное чтение бакета;
  - проксирование в nginx.

### 3.4. Документы

- **`infra/README.md`:**
  - раздел про хранилище: MinIO на VPS, где лежат данные (том `miniodata`), как посмотреть содержимое через `mc`;
  - раздел «Бэкапы»: «выключены в MVP» и явный риск — при потере сервера или диска база и фото не восстанавливаются. Включение:
    1. раскомментировать переменные;
    2. завести приватный бакет вне сервера;
    3. `--profile backup up -d`;
    4. проверить восстановление.
    
    Пометка: при включении в бэкап нужно добавить и содержимое бакета медиа (том `miniodata`) — это отдельная доработка.
  - из чек-листа после деплоя убираются пункты про бэкапы (кроме пометки «включить позже»), пункт «фото лендинга грузится через `/media`» остаётся.
- **Корневой `README.md`:** короткое упоминание, что медиа в prod хранятся в MinIO на сервере.

## 4. Что не меняется

- Код backend и frontend (кроме текста политики конфиденциальности и e2e).
- Dev-стек (`just dev`) — уже на MinIO.
- Образ бэкапа и его тест в CI.
- CD и `deploy.sh`: образов по-прежнему четыре, `backup` собирается, но в MVP не запускается.

## 5. Проверка

- `just prod-config` с `prod.env.example`, где переменные бэкапа закомментированы; `up` не включает `backup` и `migrate`.
- CI-проверка: `backup` отсутствует в графе `up` без профиля.
- `just e2e`: все сценарии плюс новый сценарий с фото.
- Тесты backend и frontend, lint, actionlint, `bash infra/backup/test.sh` (задел цел).
